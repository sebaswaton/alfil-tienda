\section{Resumen ejecutivo}

Alfil Tienda es una vitrina comercial B2B para presentar únicamente los productos con stock confirmado y conducir al cliente hacia una cotización asistida. No es un comercio electrónico transaccional: no tiene carrito, checkout ni pasarela de pago. La propuesta conserva la identidad visual de Alfil, con fondo blanco y grises claros y el verde corporativo como color de interacción.

La aplicación ya dispone de frontend React, API FastAPI, PostgreSQL y almacenamiento de objetos compatible con S3 mediante MinIO. El catálogo actual contiene \textbf{42 productos vendibles}, \textbf{2,898 unidades}, \textbf{8 categorías registradas} y \textbf{13 marcas registradas}. Se han cargado 16 productos con imagen, 22 con al menos un PDF, 88 fuentes oficiales distribuidas en 41 productos y 126 preguntas frecuentes, exactamente 3 por producto.

Para producción se decidió una arquitectura de \textbf{dos máquinas virtuales con Docker Compose}, sin Kubernetes y sin dirección IP pública. La VM web ejecutará Nginx, FastAPI y Cloudflare Tunnel; la VM de datos ejecutará PostgreSQL y MinIO. Un único dominio registrado será suficiente, con dos nombres DNS: uno para el sitio y otro para los objetos firmados de MinIO.

\begin{summarybox}
\textbf{Estado a la fecha de corte.} Las dos VM están instaladas, tienen hostname e IP estática y aceptan SSH. La VM de datos ya tiene su segundo disco XFS montado en \code{/srv/alfil}. \section{Objetivo, alcance y reglas de negocio}

\subsection{Objetivo}

Entregar una vitrina técnica y comercial que permita encontrar equipos y suministros disponibles, consultar sus características, imágenes, fichas PDF y fuentes oficiales, y solicitar una cotización a un asesor de Alfil.

\subsection{Alcance funcional vigente}

\begin{itemize}
  \item Página de inicio, catálogo, marcas, contacto, detalle de producto y página 404.
  \item Búsqueda global y filtros por categoría, marca y texto.
  \item Menú de categorías a pantalla completa inspirado en el patrón de Coolbox, adaptado a la oferta B2B de Alfil.
  \item Carrusel principal de tres imágenes con controles, indicadores y avance automático.
  \item Fichas de producto con galería, stock, SKU, número de parte, descripción, especificaciones, preguntas frecuentes, fuentes oficiales y documentos PDF.
  \item Solicitud de cotización mediante formulario y contacto directo por WhatsApp.
  \item Gestión de activos en MinIO y metadatos/relaciones en PostgreSQL.
  \item Presentación responsiva en escritorio, tableta y móvil.
\end{itemize}

\subsection{Reglas no negociables}

\begin{itemize}
  \item Solo se muestran productos con \code{status=active} y stock disponible mayor que cero.
  \item Las categorías se conservan aunque no tengan productos; deben mostrar un estado vacío correcto.
  \item No se implementan carrito, compra en línea ni pasarela de pago.
  \item Las cotizaciones y disponibilidad final quedan sujetas a validación comercial.
  \item Los archivos no se cargan directamente desde la consola de MinIO: deben registrarse mediante la API para mantener la relación en base de datos.
  \item PostgreSQL no almacena binarios; almacena datos de negocio y referencias \code{minio://...}.
  \item Las imágenes y PDF permanecen privados en MinIO y se sirven con URL firmada temporal.
\end{itemize}

La referencia visual de organización fue \href{https://www.coolbox.pe/}{Coolbox}, especialmente para jerarquía de navegación, uso del espacio, carrusel y menú amplio de categorías. El carrusel usa imágenes de extremo a extremo horizontal, controles anterior/siguiente, puntos que representan las tres diapositivas, teclado y avance automático. La interacción respeta el foco, el hover y preferencias de movimiento reducido.

\section{MinIO e integración de archivos}

\subsection{Decisión de almacenamiento}

El bucket de producción se denomina \code{alfil-catalog}. Debe ser privado. El contenido se organiza por SKU, por ejemplo:

\begin{lstlisting}
products/<sku>/images/<id-aleatorio>.webp
products/<sku>/documents/<id-aleatorio>.pdf
\end{lstlisting}

La base almacena una referencia \code{minio://alfil-catalog/...}; al responder al cliente, FastAPI genera una URL firmada de corta duración. El valor previsto por defecto es 4 horas. En producción el nombre público debe ser \code{media.<dominio>} y el endpoint interno debe continuar siendo \code{192.168.18.21:9000}.

\section{Desarrollo local y validaciones realizadas}

El entorno local usa PostgreSQL y MinIO en Compose, FastAPI y Vite. El proxy de Vite envía \code{/api} al backend local. Durante la depuración se detectaron dos procesos Vite simultáneos: uno antiguo atendía por IPv6 \code{::1} y devolvía el HTML de \code{index.html} a llamadas API, lo que provocaba errores JSON y pantallas 404. Al detener el proceso obsoleto y dejar una sola instancia, se verificaron nuevamente catálogo y detalle.

Pruebas ya completadas:
\begin{itemize}
  \item La API local devuelve \code{total=42} para productos.
  \item El catálogo y las fichas se abren correctamente en navegador.
  \item Las imágenes y PDF disponibles se relacionan con el producto.
  \item Las imágenes Docker locales del frontend y backend se construyeron.
  \item En el Compose de producción local, \code{/healthz} respondió correctamente.
  \item \code{/api/ready} respondió \code{\{"status":"ready"\}}.
  \item \code{/api/products?page_size=1} confirmó un total de 42.
  \item El backend quedó en estado saludable detrás de Nginx.
\end{itemize}

\begin{warningbox}
Si el catálogo local vuelve a desaparecer, comprobar primero que exista una sola instancia Vite y que \code{/api/products} responda JSON, no HTML. Después revisar el backend, la URL de base de datos y la carga de datos. No modificar inventario hasta descartar el conflicto de puertos/procesos.
\end{warningbox}

\section{Runbook detallado de lo que falta}

\subsection{Paso 1: cerrar preparación base de ambas VM}

Ejecutar en \textbf{cada VM} y guardar la salida en el registro de despliegue:

\begin{lstlisting}
hostnamectl
ip -br address
ip route
resolvectl status ens33
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
df -hT
systemctl is-active ssh
timedatectl
\end{lstlisting}

En la VM de datos, además:
\begin{lstlisting}
sudo systemctl daemon-reload
sudo findmnt --verify
findmnt /srv/alfil
df -hT /srv/alfil
\end{lstlisting}

Confirmar reserva o exclusión DHCP de \code{192.168.18.4} y \code{192.168.18.21}. Instalar actualizaciones con ventana controlada, verificar \code{open-vm-tools}, retirar la ISO virtual y tomar un snapshot de base limpia. El snapshot no reemplaza un backup.

\subsection{Paso 2: instalar y validar Docker}

Usar el repositorio oficial de Docker para Ubuntu, no paquetes desconocidos. La referencia operativa es \href{https://docs.docker.com/engine/install/ubuntu/}{docs.docker.com/engine/install/ubuntu}. Al finalizar, en \textbf{ambas VM}:

\begin{lstlisting}
sudo docker version
sudo docker compose version
systemctl is-enabled docker
systemctl is-active docker
\end{lstlisting}

Agregar al usuario al grupo Docker solo si se acepta que ese grupo equivale prácticamente a privilegios root; si no, operar con \code{sudo docker}.

\subsection{Paso 3: endurecimiento mínimo}

\begin{enumerate}
  \item Copiar una clave SSH administrativa y comprobar una segunda sesión antes de cambiar autenticación.
  \item Desactivar login root y, solo después de la prueba, contraseña SSH.
  \item Permitir SSH únicamente desde la red de administración/bastion.
  \item En datos, permitir TCP 5432 y 9000 solo desde \code{192.168.18.4}; 9001 solo loopback/SSH tunnel.
  \item Mantener PostgreSQL, MinIO y API administrativa fuera de Internet.
  \item Aplicar actualizaciones periódicas y registrar reinicios.
\end{enumerate}

\subsection{Paso 4: producir la release}

Desde el repositorio:

\begin{enumerate}
  \item Revocar el token GitHub expuesto y crear credenciales mínimas nuevas.
  \item Incorporar esta documentación a la rama feature.
  \item PR \code{feature/deployment-production -> develop}.
  \item Validar CI y pruebas.
  \item PR \code{develop -> main}.
  \item Crear tag \code{v1.1.0} o el número aprobado.
  \item Confirmar imágenes GHCR de frontend y backend y registrar sus digests.
\end{enumerate}

\subsection{Paso 5: desplegar la VM de datos}

En \textbf{ALFIL-DATA-PROD}:

\begin{lstlisting}
sudo mkdir -p /opt/alfil/data
sudo mkdir -p /srv/alfil/postgres /srv/alfil/minio /srv/alfil/backups/postgres
sudo chown -R administrator:administrator /opt/alfil/data /srv/alfil
\end{lstlisting}

Copiar \code{deploy/production/data/compose.yml}, la política MinIO y el script de backup a \code{/opt/alfil/data}. Crear \code{.env.production} desde el ejemplo, generar contraseñas distintas y largas, establecer \code{DATA_BIND_IP=192.168.18.21} y aplicar modo 600. No copiar ningún secreto al repositorio.

Levantar y validar:

\begin{lstlisting}
cd /opt/alfil/data
sudo docker compose --env-file .env.production pull
sudo docker compose --env-file .env.production up -d
sudo docker compose --env-file .env.production ps
sudo docker compose --env-file .env.production logs --tail=100 postgres minio minio-init
\end{lstlisting}

Verificar salud, bucket, usuario/política y persistencia tras reinicio controlado.

\subsection{Paso 6: migrar datos locales}

\textbf{PostgreSQL.} Congelar importaciones/cambios, generar un \code{pg_dump} en formato custom, calcular SHA-256, transferir por SCP/rsync, restaurar en la base productiva y comparar tablas/conteos. Mantener el dump cifrado y eliminarlo del área temporal conforme a la política.

\textbf{MinIO.} Configurar aliases de origen/destino con \code{mc}, ejecutar \code{mc mirror}, comparar cantidad/tamaño y muestrear checksum. Las referencias \code{minio://alfil-catalog/...} deben permanecer iguales.

\textbf{Criterios de migración:}
\begin{itemize}
  \item 42 productos visibles y 2,898 unidades totales.
  \item 8 categorías y 13 marcas.
  \item 16 productos con imagen y 22 con PDF como mínimo, salvo mejoras posteriores aprobadas.
  \item 88 fuentes, 126 FAQ y solicitudes existentes preservadas.
  \item Imágenes/PDF accesibles mediante firma, no por lectura pública del bucket.
\end{itemize}

\subsection{Paso 8: Cloudflare, dominio y publicación}

Crear un túnel administrado remotamente en Cloudflare. Enrutamientos:

\begin{itemize}
  \item \code{tienda.<dominio>} $\rightarrow$ \code{http://frontend:80} dentro del Compose web.
  \item \code{media.<dominio>} $\rightarrow$ \code{http://192.168.18.21:9000}.
\end{itemize}

No publicar 5432, 9001, 8000/8001 ni un hostname directo del backend. Probar DNS, TLS, redirecciones, encabezados, expiración de URLs y acceso desde una red externa. Referencia: \href{https://developers.cloudflare.com/tunnel/}{developers.cloudflare.com/tunnel}.

\subsection{Paso 9: aceptación funcional y no funcional}

\begin{itemize}
  \item Inicio, catálogo, marcas, contacto, 404 y detalle abren por HTTPS.
  \item Carrusel ocupa el ancho, flechas/puntos funcionan y no rompe móvil.
  \item Menú de categorías ocupa el viewport, anima izquierda-derecha y enlaces filtran.
  \item Buscador, filtros y paginación mantienen consistencia.
  \item La API reporta 42 productos y las categorías vacías permanecen.
  \item Se abren imágenes y PDF; un enlace vencido deja de ser válido.
  \item La solicitud de cotización queda persistida y WhatsApp usa el contacto correcto.
  \item Swagger/ReDoc no están disponibles en producción.
  \item No hay carrito, checkout ni pasarela.
  \item Se prueba escritorio, tableta, móvil, teclado, contraste y textos alternativos.
  \item Se ejecuta un smoke test de concurrencia/rendimiento y se revisan logs sin secretos.
\end{itemize}

\subsection{Paso 10: backups, monitoreo y corte}

Programar backup PostgreSQL con el script existente, retención definida y copia fuera de la VM. Para MinIO, implementar mirror a otro almacenamiento/S3. Realizar una restauración de prueba antes de producción. Alertar por caída de healthchecks, disco, memoria, errores 5xx y fallo de backup.

Para el corte, registrar tag y digest, snapshot previo, hora, responsables y smoke test. El rollback de código consiste en cambiar \code{APP_VERSION} a la versión anterior y recrear contenedores. Si hubo migración de esquema incompatible, usar un procedimiento de rollback de base explícito; no restaurar datos sin confirmar el impacto de solicitudes nuevas.

\section{Seguridad y operación}

\subsection{Controles mínimos antes de publicar}

\begin{itemize}
  \item Revocar tokens expuestos; credenciales separadas y de mínimo privilegio.
  \item \code{.env.production} con modo 600 y excluido de Git y backups no cifrados.
  \item Contraseñas diferentes para PostgreSQL, MinIO root, usuario de app y admin API.
  \item Bucket privado; URL firmada; límite MIME, firma, tamaño y nombre.
  \item Red de datos no pública; ACL por IP y puertos.
  \item SSH por clave, root deshabilitado, acceso restringido y logs de autenticación.
  \item Imágenes/servicios fijados a versión/digest; revisar dependencias y CVE.
  \item Rate limit, anti-spam y/o CAPTCHA para el formulario antes de exposición masiva.
  \item Política de privacidad y tratamiento de datos de contacto.
\end{itemize}

\subsection{RPO, RTO y retención por definir}

El negocio debe aprobar cuánto dato puede perder y cuánto tiempo puede permanecer fuera de servicio. Como punto inicial: backup PostgreSQL diario, retención local corta y copia offsite; mirror diario/incremental de MinIO; prueba de restauración trimestral. Los snapshots vSphere son auxiliares y no sustituyen backups independientes.

\section{Definición de terminado}

El despliegue se considera terminado cuando se cumplen y documentan todos los puntos siguientes:

\begin{enumerate}
  \item Release aprobada en \code{main}, tag y digests registrados.
  \item Docker saludable y reinicio automático validado en ambas VM.
  \item PostgreSQL y MinIO persistentes, privados y accesibles solo según la matriz de red.
  \item Catálogo productivo con 42 productos/2,898 unidades y relaciones verificadas.
  \item Sitio accesible por HTTPS mediante dominio definitivo, sin IP pública.
  \item Imágenes, PDF, consulta y WhatsApp validados desde una red externa.
  \item No existen secretos en Git, logs, PDF ni historial de comandos compartido.
  \item Backup automático exitoso, copia offsite y restauración de prueba registrada.
  \item Monitoreo/alertas y responsables de soporte definidos.
  \item Procedimiento de actualización y rollback probado.
  \item Aceptación funcional y visual de gerencia registrada.
\end{enumerate}

Si Docker no está instalado, instalarlo desde el repositorio oficial. Cuando ambas respuestas sean correctas, continuar primero con \textbf{ALFIL-DATA-PROD}: crear rutas, secretos y levantar PostgreSQL/MinIO. Solo después migrar datos y desplegar \textbf{ALFIL-WEB-PROD}.
